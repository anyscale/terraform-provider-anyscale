release-note:new-resource
resource/anyscale_cloud_access: Manage the complete member list of one Anyscale cloud - each member's base_role, the deny_roles restricting it, and their roles on the projects your configuration names. This resource is authoritative: create, update, and delete manage real cloud access, and anyone not declared in `member` is revoked, including on the first apply. Because that first apply revokes people Terraform has never read, and who therefore appear nowhere in the plan otherwise, `terraform plan` on a create reads the cloud's current members and warns, by name, about everyone it is about to revoke - if that read itself fails, the plan says so explicitly rather than proceeding silently. Organization admins are the one stated exception: they are invisible to the endpoint this warning reads, so it cannot name them, but this resource also never grants or revokes an org admin's access, so that blind spot matches what an apply can actually affect. Structural refusals protect against known-broken configurations: a cloud with `auto_add_user` enabled, one carrying a group policy binding, an empty `member` map (override with `allow_empty_member_set`), and declaring an organization admin as a member all refuse `create`/`update` - the backend independently and unconditionally refuses to change an org admin's cloud role regardless, and this resource never grants or revokes one. Your own identity is excluded from every read and write. Drift detection has a real limit worth knowing before relying on a clean plan: an administrator changing a member's role through the Anyscale console or CLI writes through a different store than this resource reads, so most such changes plan clean while the real role has moved - the one exception is a change crossing the `cloud_read_only` restriction, which this resource does detect. Manage each cloud's member list from exactly one `anyscale_cloud_access` instance; two instances managing the same cloud revoke each other's members indefinitely with no error from either. `unmanaged_grants` and `ungranted_members` are Computed diagnostics for a revoke or grant that could not complete - alert on `length(...) > 0` for either, since neither ever blocks the apply. Member project roles are reported only for the projects your configuration names, so an import reports none even for a member who holds them elsewhere. The cloud roles API is gated behind two independent organization feature flags, one for read and one for write; either being off returns an identical 501 detail, so a 501 alone does not indicate which.
