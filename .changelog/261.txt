release-note:new-resource
resource/anyscale_cloud_access: Manage the complete member list of one Anyscale cloud - each member's base_role, the deny_roles restricting it, and their roles on the projects your configuration names. This resource is authoritative: create, update, and delete manage real cloud access, and anyone not declared in `member` is revoked, including on the first apply. Structural refusals protect against known-broken configurations: a cloud with `auto_add_user` enabled, one carrying a group policy binding, and an empty `member` map (override with `allow_empty_member_set`) all refuse `create`/`update`. Your own identity is excluded from every read and write. Drift detection has a real limit worth knowing before relying on a clean plan: an administrator changing a member's role through the Anyscale console or CLI writes through a different store than this resource reads, so most such changes plan clean while the real role has moved - the one exception is a change crossing the `cloud_read_only` restriction, which this resource does detect. Manage each cloud's member list from exactly one `anyscale_cloud_access` instance; two instances managing the same cloud revoke each other's members indefinitely with no error from either. `unmanaged_grants` and `ungranted_members` are Computed diagnostics for a revoke or grant that could not complete - alert on `length(...) > 0` for either, since neither ever blocks the apply. Member project roles are reported only for the projects your configuration names, so an import reports none even for a member who holds them elsewhere. The cloud roles API is gated behind two independent organization feature flags, one for read and one for write; either being off returns an identical 501 detail, so a 501 alone does not indicate which.
